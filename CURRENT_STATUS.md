## Current standing

Macaulean has a working foundation for connecting Lean proofs with Macaulay2 computations, alongside an experimental interpreter that runs a subset of Macaulay2-style code inside Lean. The immediate challenge is to turn that interpreter into a usable, compositional verification workflow: expose the translated program, state what it should do, and prove that statement while making the remaining assumptions explicit.

The latest meetings favor **small, understandable examples before broader language expansion**. GCD remains the motivating example, but meeting 4 identified a smaller prerequisite: make a worksheet function accessible as a persistent Lean object, even starting with a function that always returns zero. The original certificate-based tactic remains relevant; the DSL is an additional direction, not an agreed replacement. [M3 00:32–00:43; M4 00:07–00:18, 01:18–01:23]

### What meeting 4 clarified

The live example evaluated a recursive integer GCD, with discussion narrowing inputs to natural numbers. An earlier polynomial GCD proposal remains a follow-on target. The subtraction version exhausted evaluation depth; changing the algorithm to use remainders improved the example. Neither observation proves general correctness or termination. [M2 01:14–01:19; M4 00:25–00:34]

The execution-only worksheet retained a function in interpreter session state, but the participants could not refer to it as an ordinary Lean declaration. Importing `Macaulean.Verification` exposed existing contract tooling, not the general function interface they wanted. This is now partially addressed by the open definition-exposure PR above. Existing parser, lexical-code, library-compilation, and contract machinery should be reused. [M4 00:34–00:48; `Interpreter/LibraryCompiler.lean`; `Verification/Frontend.lean`]

The intended workflow separates three claims:

1. **Translation:** the represented program preserves the chosen source semantics, including relevant bindings and state changes.
2. **Algorithm correctness:** for the stated input domain and primitive-operation assumptions, the represented program meets its mathematical specification; termination is a separate obligation unless included explicitly.
3. **Instance certification:** a particular returned answer satisfies a mathematical property, without proving the producing algorithm correct on all inputs.

Users must supply the mathematical claim they want proved. Translation should compose automatically from supported syntax; it should not require a new AI-written mirror implementation for every function. Per-function specifications and proofs are still expected. Full fidelity to native Macaulay2, versus a documented supported dialect, remains a design boundary to settle. [M4 00:15–00:18, 01:12–01:24, 01:29–01:40; #42]

## Proposed sequence of future goals

**First milestone — a program we can name and reason about.** Settle the development base, review DSL#1, and demonstrate an exported zero function with a simple mathematical statement. Make the runtime-value/Lean-value boundary visible. This is the smallest response to meeting 4's concrete blocker. Corresponds to A1–A3.

**Second milestone — a reusable GCD case.** Pass a small GCD through the real conversion and state exactly what is proved. A translation-preservation theorem and a GCD-correctness theorem answer different questions; retain both goals. Prove termination or adequate input-dependent depth against the actual evaluator. Its fuel bounds evaluation depth, so a bound on Euclidean iterations alone is not yet a justified interpreter bound. Test another function through the same conversion to rule out a GCD-specific implementation. Corresponds to A4–A5.

**Third milestone — useful algebraic verification.** Continue the existing arithmetic → coefficient rows → reduction → ideal-membership proof path, and choose one follow-on program to test the abstractions. Keep certificate checking available for expensive computations and make unverified primitive assumptions explicit. Corresponds to A6–A9 and A11.

**Longer-term direction — verification of M2 programs assembled from specified components.** Aim for users to write familiar M2 code, provide mathematical contracts, and obtain Lean-checked evidence with a clear account of assumptions. Extend types, package support, and automation as concrete examples justify them. A complete Macaulay2 reimplementation, Rust/JIT interpreter work, exhaustive engine verification, and broad Schubert2 formalization were exploratory ideas, not prerequisites or agreed near-term deliverables.
